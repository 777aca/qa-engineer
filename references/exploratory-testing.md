# 主动探索测试

适用于用户明确要求基于 URL 或源码检查功能、查找 Bug 的任务。先复用现有目标、档位、平台与权限；仅补充会影响结果的缺项。只给链接且意图不明时确认目的，不默认执行扫描。

## 1. 档位与范围

| 档位 | 目标 | 在所选功能范围内追加的检查 |
|---|---|---|
| L0 | 环境与首屏冒烟 | 文档响应、关键元素、资源与错误日志；不交互 |
| L1 | 业务主流程 | 正确输入、主操作和业务结果断言 |
| L2（默认） | 业务闭环与关键异常 | 创建/查询/更新等获授权操作的一致性、空值、错误反馈、刷新 |
| L3 | 边界与交互细节 | 依据业务规则的输入边界、列表状态、键盘和响应式 |
| L4 | 已授权的专项检查 | 安全、可访问性、性能或功能性源码审查 |

高档位包含适用的低档位检查，但不扩大功能范围、平台或操作权限。安全探针与压测要各有授权，不能因选择 L4 自动执行。缺少测试账号、规则或环境时记录 Blocked，不能降级后声称完成该档位。

预计耗时取决于页面和流程数量，不承诺固定时间或 Bug 数量。没有发现问题也是有效结果。

## 2. 平台

- 默认 PC，基线 1280×800；L3+ 可增加 1920×1080。
- 移动端基线 375×667，L3+ 增加 390×844、768×1024。
- L0–L2 只用选择的平台基线，不擅自添加断点。
- PC/Mobile 分别保留执行结果，再按根因归并缺陷；不能用其中一次的结果覆盖另一平台。
- 内置扫描器使用 Chromium 的视口、touch 和 mobile 模拟；不代表真实 iOS Safari、真机软键盘或原生 App 已验证。需要这些能力时按任务使用相应设备/浏览器。

## 3. URL 探索流程

1. 读取已有需求、路径与测试入口，确认可访问域名、账号、允许执行的操作和清理方式。
2. 用现有浏览器工具打开页面，等待关键元素；收集页面标题、可见表单、按钮、导航与首屏错误，不默认点击全部按钮或访问所有外链。
3. 按业务目标制定本轮检查点。预期优先来自需求和接口契约；从 UI 推断的规则明确标为假设。
4. 执行适用场景，逐步验证业务结果。例如保存后重新查询或刷新，确认值仍存在；列表筛选后核对结果内容与数量。
5. 出现可疑点时保存脱敏证据、最小复现路径和状态。异常日志、请求失败、布局截图首先是观察，不自动升级为已确认业务 Bug。
6. 汇总实际覆盖与未完成项，生成结构化用例和缺陷清单。

### 内置扫描器与业务场景

参考 [扫描器说明](../docs/scan-runner.md)。内置规则负责页面基础检查与有限的密码登录专项，业务场景由配置中的明确操作和断言执行。

L1+ 未配置适用场景会记录“业务主流程覆盖：Blocked”。已有场景通过只证明其声明的路径，不代表整个网站完成测试。

生成场景前先观察真实控件，用 role/name、label 或稳定 test_id 定位；CSS 是已有稳定选择器的备选。配置不运行任意 JavaScript。凭据使用 fill_env，登录态使用 --storage-state。

默认阻止非 GET/HEAD/OPTIONS 请求；依赖 POST 查询的页面也可能被阻塞，需要在获授权后使用 --allow-submit。该参数只是把既有授权传给执行器，不能扩大用户许可。需要额外登录域名时显式配置 allowed_origins，不自动跟随越界导航。

### 没有浏览器或环境不可达

报告访问失败或依赖缺失，继续可独立完成的源码分析/用例设计。静态 HTML 无法证明浏览器交互、鉴权或后端数据闭环。不要把静态推断标成已执行通过。

## 4. 源码探索

先阅读业务入口、路由、数据流、接口契约与已有测试，再识别会造成实际功能问题的路径。

- 能从代码证明的问题，写清触发输入和完整执行路径，证据标为 code；注明尚未运行。
- 依赖后端、浏览器或未明确业务规则的假设，标为待验证并给出验证用例。
- 不把 useEffect 依赖、列表 key、异步未取消等模式直接判成 Bug；要说明实际触发条件和用户可见后果。
- 没有运行时验证的用例保持未执行，不填写 Pass。

## 5. 候选检查维度

仅选取本轮范围、档位与授权允许的条目，不逐项强制执行。

| 维度 | 可检查内容 | 判定注意点 |
|---|---|---|
| 页面与资源 | 主体渲染、加载态、空态、资源失败、异常日志 | 短 HTML 和第三方日志不等于白屏或核心功能失败 |
| 表单 | 必填、格式、需求定义的长度/数值边界、特殊字符 | 禁用按钮和原生校验可有效阻止提交；空格处理须验证提交结果 |
| 列表 | 搜索、筛选、排序、分页、空结果、状态保持 | 核对数据与条件一致性，不只检查按钮能点击 |
| 编辑与上传 | 保存后重新查询、文件格式/大小限制、取消与错误反馈 | 只用获授权测试数据，明确清理规则 |
| 状态与并发 | 刷新、回退、请求乱序、重复动作 | 多个请求不证明重复落库；按业务规则核对最终状态 |
| 网络异常 | 超时、离线、401/403/500 的反馈与恢复 | 先证明异常到达被测路径，避免把前置校验误当网络处理 |
| 响应式 | 所选平台断点的遮挡、溢出、操作可达性 | 截图需要复核；不把采集成功当布局通过 |
| 可访问性 | 可访问名称、标签关联、图片替代文本、键盘与焦点 | 装饰图允许 alt=""；name 属性不等于可访问名称 |
| 安全专项 | 明确范围内的输入回显、访问控制、会话属性 | 单一探针不代表完整安全审计；不采集凭据值 |
| 性能专项 | 用户指定指标、负载与持续时间 | 与被测环境容量及压测授权一致，参考性能专用资料 |

可访问性需要深入检查时，可以使用已安装的 axe-core 等工具并结合人工检查；内置 DOM 检查不能证明完整 WCAG 合规。

## 6. 结果与证据

检查结果使用以下状态，缺陷确认程度是独立字段：

| result | 含义 |
|---|---|
| Pass | 已执行本检查的断言并满足预期 |
| Fail | 有明确预期，运行时断言未满足 |
| Skipped | 当前页面不适用或本条未覆盖，注明原因 |
| Blocked | 缺账号、规则、授权、环境等前置条件 |
| Error | 执行器、定位、浏览器或证据写入失败 |
| NeedsReview | 采集到候选信息或截图，需要复核 |

缺陷默认 status=待验证、reproducible=一次。只有证据足以支撑期望与实际不一致时才标已确认；重复执行并观察到一致结果后才判断必现/偶现。

- 证据可包含断言、Console、Network、源码位置和截图。截图失败不能留下一个伪造的图片路径。
- 报告中不出现密码、Token、Cookie 值或凭据前缀；扫描器存储检查只采集键名。
- 截图默认遮罩输入控件及 data-qa-sensitive 元素。页面其他个人信息仍需交付前复核。
- --trace 显式开启失败 Trace；其原始 DOM/网络内容不能保证脱敏，放在输出目录的 private-traces，仅本地调试，不进入普通报告或自动上传。
- 无异常、零缺陷、没有返回结果都不能替代通过证据。

## 7. 交付与数据契约

用例统一采用 [output-formats.md](output-formats.md) 的 preconditions 字段。旧 precondition 可无冲突转换，两个字段值不一致时必须报错。PC/Mobile 采用独立用例 ID，保留平台、档位、状态、证据和关联 Bug。

扫描器直接产出 test-cases.json/yaml/xlsx、bugs.json/yaml、bug-report.xlsx 和 summary.json。需要 XMind 时将同一份 test-cases.json 传给转换脚本。

所有检查点（包括失败、跳过、阻塞）都进入用例清单。手工或 Agent 补充的场景也必须包含明确步骤、预期、实际结果和执行状态，不能根据“没发现 Bug”批量补 Pass。

用户指定目录优先；正式报告遵循项目 docs/，临时评审遵循 discuss/。默认扫描产物位于 samples/out/。单个已确认高优先级 Bug 的展开格式参考 [bug-report.md](bug-report.md)，是否提交工单由用户授权决定。
